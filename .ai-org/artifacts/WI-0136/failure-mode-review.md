# WI-0136 failure-mode review

## Conclusion

The repeated stops were primarily experiment-harness defects, not repeated evidence that Temple or the selected models failed the delivery task.

From representative protocol v3 through evaluator continuation v15, eleven live attempts stopped:

- ten exposed incomplete runner, isolation, or Provider-event compatibility handling;
- one was the intentional v4 Design Operational-Token ceiling; and
- zero produced a completed arm-blind Temple-versus-baseline judgment.

V13 later completed all ten candidate turns, both arms, all objective tests, and exact cold recovery. Its evaluator still stopped, but the old runner masked the Provider terminal behind a missing-usage message. The underlying v13 cause therefore remains unknown. The separately approved v16 continuation then completed the frozen arm-blind evaluation successfully without regenerating candidate work.

## Why narrow repairs kept failing

Each successor reproduced the one event shape just observed, while adjacent states remained untested. The runner had separate assumptions about command presentation, cwd authority, filesystem aliases, process lifetime, terminal ordering, Token notifications, output-schema acceptance, semantic output validation, and evidence persistence. Fixing only the latest assumption moved the first uncovered boundary rather than proving the complete path.

The Codex App Server documents `turn/completed` as a terminal that may be completed, interrupted, or failed, while detailed Token usage arrives through a separate notification. Those streams must be correlated without allowing missing usage to hide a failed terminal. See the [Codex App Server reference](https://developers.openai.com/codex/app-server).

The v13 terminal was not retained, so it is not valid to infer that numeric schema bounds caused the failure. OpenAI documents numeric constraints in Structured Outputs and documents Structured Outputs support for GPT-5.6 Sol. The v15 integer enum is a smaller contract and a useful hardening measure, not a proven diagnosis of v13. See [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

## Systemic repair through v16

V15 added the first evaluator-only production-path rehearsal, but the injected launcher returned a completed turn directly and therefore did not exercise the real `item/started` classifier. V16 closes that specific gap and keeps the rest of the systemic repair:

1. Generate the output schema from the exact two package IDs, eight dimension IDs, five permitted critical-failure values, and binary scores.
2. Bind the exact evaluator instruction digest and byte count.
3. Validate the exact `thread/start` and synthetic `turn/start` request shapes against schemas generated by the installed Codex CLI.
4. Extract all nineteen installed item types, freeze their passive-versus-denied partition, accept normal reasoning and message events, and reject every active tool class.
5. Exercise the real continuation function with the immutable v13 candidate and an injected zero-Token evaluator.
6. Validate semantic output, freeze scores before mapping unseal, and run the real analyzer.
7. Release waits on a terminal, abort, child-process exit, or deadline so a missing terminal cannot hang indefinitely.
8. Preserve Provider terminal details, transport failures, observed item types, usage, and semantic-validation failures in the stopped evidence instead of replacing them with a later symptom.

The v16 durable readiness record contains fourteen passing checks, zero Operational Tokens, zero retry, zero fallback, and `model_generation_performed: false`. After exact human approval, all twenty-three live preflight checks passed. The evaluator completed once in 37.693 seconds with 20,860 Operational Tokens, zero retry, zero fallback, no tool activity, frozen scores before mapping unseal, and no critical failure in either anonymous package.

## Interpretation boundary

This repair materially lowered the risk of repeating the known harness classes and completed the bounded v16 path. It does not prove that a future Provider or model can never return a new failure. The completed evidence shows that v16 retained the terminal, observed item types, usage, score-freeze order, and final analysis needed to diagnose or reproduce this run without guessing.
