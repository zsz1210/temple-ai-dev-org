# Can a fresh Agent resume work more reliably with Temple?

Status: design proposal only. No fixture, runner, frozen protocol or live run is
created by this document. See [approved scope](brief.md).

## The decision this should inform

Should Temple invest further in its repository-backed takeover path, rather than
continue optimizing entry formats for small isolated tasks? Test whether a new
Agent preserves completed work, follows current requirements and finishes the
remaining change with less rediscovery or fewer recovery errors than a competent
ordinary workflow. Do not make passing Temple administration the primary outcome.

[WI-0203](../WI-0203/report.md) found equal measured acceptance but greater Temple
resource use on one clear small-feature pair per model. Its scope did not cover
interrupted work or changed requirements. [WI-0224](../WI-0224/result-report.md)
retained an incomplete format comparison whose sole completed pair reversed the
earlier direction; it cannot establish a preferred default. [WI-0225](../WI-0225/design.md)
already retained continuity as a separate unanswered question.

The recent exact-text rehearsal was a local scripted administration check, not
fresh-Agent evidence. It must not be pooled with this comparison. Mechanical
completion is excluded from the proposed task; normal Developer/Verifier
responsibilities remain unchanged.

## One product, two takeover states

Use a small, offline, single-repository order-quote module with integer minor-unit
amounts. The future fixture contract must specify discount-before-shipping order,
threshold inclusivity, supported inputs and errors, and the public return shape.
No UI, live service, credentials, package installation or microservice orchestration.

| State | Shared starting truth | What the new Agent must do |
| --- | --- | --- |
| A: stable partial work | Discount calculation is already implemented and accepted; shipping integration and its boundary case remain unfinished. | Preserve the completed calculation, implement only remaining approved behavior, test the exact resulting revision. |
| B: an approved requirement changed | The same partial implementation exists, but an explicitly approved current specification changes the shipping threshold from the prior revision; an old passing test record remains historical. | Identify current authority, retain unrelated completed work, implement the current threshold and avoid treating the old pass as current verification. |

These are deterministic checkpoints, not simulated natural interruption times or
claims about real interruption frequency. Seed history and test observations from
actual fixture commands, never fabricate a passing result. State A checks that the
test does not require a stale-document trap to show value; State B tests realistic
version reconciliation. Both arms get the same old and current facts and ordering.

## Fair comparison

Both arms receive identical product Git history and working state, current spec,
public tests, tool permissions, runtime, model/effort, and a concise handoff. The
handoff names the accepted candidate, completed work, remaining scope, known test
status, current spec revision and changed requirement when applicable. Do not give
the ordinary arm an empty repository, missing handoff or an ambiguous obsolete spec.

The intervention is the representation and mandatory administration of continuity:

- Ordinary: normal repository documents, Git, tests and the concise handoff. The
  Agent may inspect, search and plan competently; do not prohibit useful habits.
- Temple: the same underlying facts plus canonical Work Item, scope/authority
  references, current ownership and the documented recovery route. Obsolete claims
  are reconciled before launch; never let a new Agent steal an active claim. Native
  instructions and required reads stay intact. Do not carry over hidden predecessor
  conversation, summaries or memory to either arm.

Before dispatch, compare an arm-neutral fact inventory. Every decisive product or
handoff fact present in Temple must be available in the ordinary documents. The
ordinary arm must not contain Temple instructions or extra historical conversation;
Temple must not contain oracle answers. The product file hashes match before each
paired launch. Framework-only differences are listed, not silently normalized away.

## Endpoint and objective acceptance

This is a **Build-stage takeover** comparison, not a complete lifecycle benchmark.
End each subject at a submitted exact product candidate and its handoff. Temple
may finish Developer Build into Test; it must not claim Done or Independent QA.
Ordinary submits the equivalent candidate and findings. A separate deterministic
runner then checks both candidates with the same held-out product oracle.

The oracle must check both revisions' boundary behavior, discount preservation,
unchanged public API and regression tests. A stale candidate that passes only old
tests must fail. Missing candidate, modified protected tests, unauthorized scope or
unresolved acceptance does not become a pass through good prose or a lifecycle flag.
The invariant-protected completed module and allowed change paths are declared in
both briefs before launch; allowed implementation freedom is otherwise symmetric.

Actual downstream human/AI review and Temple's distinct Verifier are outside this
endpoint and must be shown as excluded, not zero. A favorable result can motivate
a separately scoped end-to-end evaluation, not an immediate total-delivery claim.

## Measurements and interpretation

| Measure | Definition and limit |
| --- | --- |
| Correct recovery | Current-spec oracle passes; completed behavior and protected scope preserved; exact candidate and remaining-work account agree. Report separately for A and B. |
| Recovery errors | Wrong revision, stale verification accepted as current, loss of completed behavior, unauthorized overwrite or unresolved dependency. Use predeclared observable categories. |
| Duplicate work | Recorded edit/restore of already-complete protected work or repeated identical product test at unchanged relevant inputs. Necessary rereads or regression tests are not automatically waste. Unobservable reasoning stays unknown. |
| Human interventions | Each correction/request for missing information and its cause. Essential new business judgment is not a failure of the Agent. |
| Time | Provider stage wall time and measured harness/preparation time separately. Tool-notification gaps are not model thinking time. |
| Usage | Raw input, cached input, output, total, and operational input-minus-cache-plus-output. Missing fields remain unknown. No monetary estimate without a verified price basis. |
| Preparation burden | Actual per-arm setup commands, written artifact bytes and measured preparation time. Shared synthetic fixture construction is separately listed. No-model preparation has zero subject-model Tokens, not zero engineering effort. |

Report cold takeover cost separately from preparation, but show their observed sum
where compatible and list excluded coordinator, framework-development and later
review costs. Do not amortize setup across imaginary future tasks. A long-context
read alone does not prove an error or wasted Tokens. Archive every attempted subject,
including incomplete pairs; keep all-attempt totals apart from completed-pair deltas.

## Offline qualification before spending on subjects

Use the real intended CLI/runner path, not a disconnected mock-only substitute:

1. Build the two checkpoints and verify the shared fact inventory and product hashes.
2. Confirm an objectively correct completion passes in both arms.
3. Seed a stale-threshold implementation and a damaged completed module: each must
   fail the corresponding oracle in both arms, even with a polished handoff/pass flag.
4. Replay first-stop classification, trailing completion, revision grammar, missing
   usage and cleanup against the same harness modules intended for live dispatch.
5. Prove subject isolation: no previous chat, shared writable checkout, answer files,
   running provider process or changed source persists into the next subject.

Pin source/fixture/contract/harness hashes only after these checks pass. A fixture
failure is an instrument problem, not a model-quality sample. Do not patch a running
experiment or rewrite a frozen old protocol to obtain a passing sample.

## Bounded live proposal, not authorization

A diagnostic layout would use two states, each with an ordinary-first pair and a
Temple-first pair: eight fresh takeover subjects, one fixed model/effort, no automatic
retry or fallback. This is order coverage, not a statistically justified sample size
or eight complete delivery/QA cycles. Terra medium is a current policy-supported
candidate, not a claim of optimality; the launch protocol must verify availability,
effective settings and budget without substituting a model silently.

Before live execution, a separate reviewed protocol must set the useful improvement
needed for further investment, permissible cost/time tradeoff, exact maximum usage
and duration, privacy/persistence contract and appropriate authorization. Use retained
baseline distributions and the maintainer's value of avoided recovery mistakes;
do not invent a percentage, treat old caps as current approval or buy more samples
because the result is unconvincing. These launch choices remain deliberately unset.

An actor failure ends that subject without replacement. Continue an unrelated
subject only after predeclared isolation checks establish local impact. Shared
validity, privacy, cleanup or usage uncertainty stops the entire run. Aggregate
limits override pair completion. All partial costs and reasons remain visible.

## Predeclared outcome directions

- Any authority/scope regression blocks recommending the tested Temple route until
  diagnosed. A candidate failing the product oracle cannot win on cheapness alone.
- Preserved correctness plus a useful continuity improvement within the approved
  resource tradeoff supports further bounded continuity work for the tested shape.
- Equal correctness with only higher overhead, or no useful recovery improvement,
  means stop adding machinery for this shape; prefer ordinary workflow or narrower
  opt-in use. Do not rescue the result with another model/format matrix.
- Mixed directions or incomplete coverage remain inconclusive; retain the existing
  default and explain missing evidence. No automatic extension or broad efficiency
  claim. Any later study needs a new decision it could actually change.

Completion of WI-0230 means this design has been reviewed and retained. Fixture
implementation, offline qualification, budget selection and live launch are future
work, not completed or authorized by this design's acceptance.
