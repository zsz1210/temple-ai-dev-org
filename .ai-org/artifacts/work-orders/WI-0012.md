# Work Order — WI-0012

## Outcome

Keep bounded Codex history useful without presenting it as an active runtime. Replaying an equivalent provider snapshot must be idempotent, and the Dashboard must distinguish historical evidence from current live observations.

## Evidence entering Design

- The Alpha.26 Dashboard connected successfully to the local Codex App Server and reconciled the only registered terminal task without attempting `thread/resume`.
- The resulting projection nevertheless counted that task as `live` because any retained task event was treated as a live observation.
- Repeated startup accumulated equivalent history because reconciliation event identity included the current snapshot observation time.
- The journal is recoverable generated state under the Git common directory; canonical Work Items and repository evidence remain in `.ai-org/`.

## Approved scope and design

1. Derive reconciliation occurrence fallbacks from stable provider or registered-task timestamps and derive reconciliation identity from the normalized event time and semantic state, not the current observation time.
2. Prove that two equivalent snapshots observed at different times yield identical identities and append as duplicates rather than new records.
3. Split task records into provider-reconciled history and non-reconciled live notifications.
4. Count a task as `live` only when it is eligible for live resume and has a non-reconciled runtime observation.
5. Introduce `history-only` visibility and `historical` provenance for reconciled observations. Historical failures must not become current runtime-failure attention.
6. Add Dashboard styling and a separate history-only counter.
7. Preserve `registered-only` for ready providers with no observations and `unknown` when neither a usable observation nor a ready provider exists.

## Risk review

- Stable identity must still change when provider thread, turn, item, status, lifecycle, item status, revision correlation, or normalized occurrence time changes.
- Historical data remains evidence, but cannot imply an attached live subscription.
- Existing live notification behavior must remain unchanged.
- Journal repair uses the existing archive-and-rebuild operation; no canonical repository data is deleted.
- No Codex model turn, external write, publication, deployment, model switch, or spending is authorized.

## Verification

- Focused snapshot-idempotency, terminal-history, live-observer, and Dashboard tests.
- Full `npm run verify` at the exact candidate revision.
- Fresh detached Independent QA at the same revision.
- Stop the current local server, archive/rebuild generated telemetry, restart with the real Codex Provider, and inspect the loopback snapshot.

## Rollback

Revert the candidate commit and restore the archived generated journal if historical runtime telemetry is needed for diagnosis. Canonical Work Items, repository events, and evidence remain unaffected.
