# WI-0001 Work Order and Design

- Status: approved
- Approved at: 2026-08-30
- Product owner position: Product Manager
- Technical owner position: Tech Lead
- Implementation owner position: Developer
- Approval source: project owner direction recorded through the Temple self-hosting workflow

## Outcome

Make the documentation navigable by a new reader without erasing the historical boundaries between current guidance, architecture decisions, research, pilots, and validation evidence.

## Acceptance criteria

1. `docs/` exposes a stable, shallow, purpose-based hierarchy and a human-readable index.
2. Current English guides are grouped under getting started, concepts, operations, extensions, or planning.
3. ADRs, validation records, research records, and pilot records keep their existing semantic meaning.
4. Every repository-local Markdown link resolves after the migration.
5. The repository language policy continues to pass.

## Technical design

Use these top-level documentation categories:

- `getting-started/` for adoption, operation, and testing guidance.
- `concepts/` for the framework model, specifications, and design contracts.
- `operations/` for collaboration, orchestration, assurance, evidence, and control-plane operation.
- `extensions/` for capabilities, context, learning, Skills, adapters, and migrations.
- `planning/` for the roadmap and forward-looking plans.
- `adr/`, `validation/`, `research/`, and `pilots/` for immutable or evidence-oriented records.

Keep the hierarchy no deeper than necessary. Preserve file content during mechanical moves, then update links and navigation with explicit patches.

## Risk review

- **Broken links:** run the repository Markdown link checker after every migration wave.
- **Historical rewriting:** do not rewrite validation or pilot conclusions merely to match current positioning.
- **Unreviewable rename noise:** group moves by purpose and keep navigation changes separate from semantic claims where practical.
- **Localized drift:** keep localized roadmap files together and verify all three language entry points.

## Exclusions

- No wiki publishing or external documentation hosting.
- No semantic search or RAG implementation.
- No change to framework authority or runtime behavior.
