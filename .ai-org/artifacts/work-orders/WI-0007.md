# WI-0007 Work Order and Technical Design

- Status: approved
- Approved at: 2026-08-30
- Engineering owner position: Tech Lead
- Implementation owner position: Developer
- Approval source: project owner authorized Phase 4A implementation after accepting the Phase 4 durability design

## Outcome

Provide a recoverable local backup and restore path for Temple's project-owned organization state. The first slice must be inspectable, content-addressed, stale-plan-safe, and recoverable after a partial write without claiming to back up the application's complete repository or provide remote disaster recovery.

## Backup boundary

Include:

- `temple.lock`;
- project-owned `AGENTS.md` when present;
- `.ai-org/project/**`, `.ai-org/learning/**`, `.ai-org/work-items/**`, `.ai-org/decisions/**`, `.ai-org/events/**`, `.ai-org/artifacts/**`, and `.ai-org/adapters/**`;
- files under `.agents/skills/**` that are not exact `temple.lock.managed_files` entries.

Exclude:

- `.ai-org/views/**` generated projections;
- framework-managed `.ai-org/core/**`, `.ai-org/templates/**`, managed Skills, Position configs, `TEMPLE.md`, and `templew.mjs` because the pinned framework can reconstruct them;
- local control-plane telemetry below the Git common directory;
- application source, product documents outside the declared Temple boundary, Git objects, dependencies, credentials outside included files, and external systems.

## Backup format

- Use a transparent directory snapshot with `manifest.json` and `files/<repository-relative-path>`.
- Manifest schema: `temple.backup-manifest/v1`.
- Record project ID, Temple version, exact Git revision when available, whether the working tree was dirty, created time, format, boundary, exclusions, sorted file entries, mode, size, SHA-256, and a deterministic digest of the file table.
- Refuse unsafe paths, symbolic links, duplicate paths, oversized individual files, excessive total size, or excessive file count.
- Build in a unique sibling staging directory and rename only after the complete payload and manifest verify.

## Inspection and restore planning

- Inspection validates the schema, supported format, path safety, uniqueness, ordering, project metadata, size bounds, payload file set, file sizes, modes, hashes, and content digest.
- Restore planning is read-only and reports `create`, `identical`, and `replace` actions plus extra target files that Temple will preserve.
- Require backup and target project IDs to match when the target already has project identity.
- Refuse a backup created by a newer Temple version. Allow an older version but report `upgrade_required=true`.
- Compute a deterministic restore-plan digest over target identity, manifest digest, action paths, before hashes, after hashes, and compatibility state.

## Restore transaction

- `restore apply` requires `--expected-plan` matching a fresh preview.
- Existing different files require `--allow-replace`; there is no force-delete mode.
- Revalidate every destination immediately before writing.
- Keep one active recovery transaction per target outside the worktree, preferring the Git common directory and otherwise a safe sibling state directory.
- Before mutation, persist a ledger and before-images for every planned write. Update the durable ledger after each successful target write.
- On an ordinary error, roll back immediately. On simulated process interruption, leave the active ledger for `restore recover`.
- Recovery restores or removes only paths whose current digest still matches Temple's recorded partial write. If another actor changed a path, refuse rather than overwrite it.
- Completed and rolled-back ledgers retain bounded path and digest audit metadata; remove before-image contents and prune older terminal transactions.

## CLI surface

```text
temple backup create <target> --output <directory>
temple backup inspect <target> --backup <directory>
temple restore preview <target> --backup <directory>
temple restore apply <target> --backup <directory> --expected-plan <sha256> [--allow-replace]
temple restore recover <target>
```

Every command supports `--json`. Inspect and preview never mutate canonical state. Backup creation writes only the explicit external destination. Apply and recover run under the existing project mutation lock.

## Test design

- Back up an initialized data-bearing fixture with a project Skill and prove managed files and generated views are excluded.
- Reject traversal, duplicate, unordered, missing, extra, symbolic-link, size, and digest tampering.
- Prove preview is read-only, reports action types and extras, and becomes stale after target mutation.
- Refuse replacement without permission and project/version incompatibility before mutation.
- Apply to a clean initialized environment, preserve extras, rebuild views, and pass Doctor.
- Inject an ordinary write failure and prove immediate rollback.
- Simulate interruption after a partial write, prove the active ledger remains, recover, and prove exact before-state restoration.
- Change a partially written path after interruption and prove recovery refuses to overwrite it.
- Rehearse an older-version backup that restores with an explicit upgrade-required result.

## Risk review

- **Backup mistaken for whole-project backup:** manifest and documentation name the exact inclusion and exclusion boundary.
- **Archive traversal or symlink escape:** accept only normalized repository-relative POSIX paths and regular files.
- **Silent overwrite:** preview digest, stale-target recheck, project identity, and `--allow-replace` are mandatory.
- **Crash after partial apply:** persist before-images and applied hashes before and during mutation.
- **Rollback overwrites new work:** rollback only when the current file still matches Temple's after-hash.
- **Secret persistence:** backup contents may contain project secrets already stored inside the included boundary; warn users to protect the destination. Ledgers remove before-image contents after terminal state.
- **Unbounded storage:** cap files and bytes, retain only bounded terminal ledgers, and do not copy runtime telemetry by default.
- **Version drift:** refuse newer backups, label older restores for upgrade, and record exact backup schema and Temple version.

## Exclusions

- Remote or cloud backup transport, encryption-key management, compression, schedules, and notifications.
- Full Git repository, application database, dependency, build artifact, or external-system backup.
- Automatic deletion of target files or conflict resolution.
- Distributed transactions, distributed exactly-once behavior, multi-machine consensus, or production disaster-recovery certification.
- Automatic upgrade or rollback across Temple versions.
