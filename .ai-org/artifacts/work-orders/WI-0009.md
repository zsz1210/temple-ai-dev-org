# WI-0009 Work Order and Technical Design

- Status: approved
- Approved at: 2026-08-30
- Engineering owner position: Tech Lead
- Implementation owner position: Developer
- UI delivery mode: code-first
- Approval source: project owner accepted the recommendation to fix dogfood Dashboard reliability before Phase 4B

## Outcome

Make the local Dashboard truthful and promptly available for a real long-running Temple task. Terminal Work Items must not appear queued, and opting into the Codex provider must not make HTTP availability depend on an unbounded initial history import.

## Root causes

1. `categoryFor` has no terminal branch, so every non-blocked, non-QA, non-release, unclaimed Work Item falls through to `queued`, including `done` and `cancelled`.
2. `startControlPlaneServer` awaits `codexProvider.start()` before constructing and listening on the HTTP server.
3. Provider startup requests `thread/read` with all turns, normalizes every turn and item, then may normalize the full thread returned by `thread/resume` again.
4. Snapshot normalization has no turn or item bound, so a long registered task can create thousands of journal events during startup.

## Design

### Terminal lifecycle category

- Categorize `done` and `cancelled` as `terminal` before active-runtime checks.
- Add `terminal` to Observer category counts and the Dashboard metric row.
- Render terminal badges with the existing successful/settled visual treatment.
- Keep blocked, approval-pending, QA-pending, active, and queued meanings unchanged.

### HTTP-first startup

- Construct the Codex provider object before the server so Inbox routing retains the provider reference.
- Start the loopback HTTP listener, write daemon metadata, and return the usable control-plane handle without awaiting Codex history synchronization.
- Start Codex connection and reconciliation in a retained background promise after the listener is available.
- Keep provider state offline, degraded, ready, registered-only, or unknown according to observed capability; do not infer completion while background startup is pending.
- On close, stop the provider and settle the retained startup promise so no rejection or reconnect escapes shutdown.

### Bounded reconciliation

- Default the initial snapshot window to the latest 20 turns and at most 200 items across those turns.
- Permit explicit project-provider options within guarded ranges: 1–100 turns and 1–1000 items.
- Always retain the thread status event.
- Select newest turns and newest items while preserving their chronological order in normalized output.
- Mark reconciled records with the available and retained counts plus a truncation flag.
- Reconcile the `thread/resume` response only when `thread/read` did not already produce a snapshot; live notifications remain unbounded by the startup snapshot window but continue through journal retention and privacy limits.

## Verification

- Unit-test `done` and `cancelled` category behavior and category totals.
- Unit-test bounded snapshot selection with more turns and items than the configured window.
- Start a control plane against a fake App Server that deliberately never completes `thread/read`; prove `/healthz` and `/api/v1/snapshot` are available before provider synchronization finishes.
- Retain the existing App Server handshake, reconciliation, privacy, request-memory, replay, condition, and HTTP tests.
- Run the full repository verification and visually inspect the self-host Dashboard against canonical Temple state.

## Risks and mitigations

- **Recent context omits an older causal event:** expose truncation metadata and keep live events; the Dashboard is an operational projection, not the canonical conversation archive.
- **Background startup failure becomes invisible:** provider status and degradation reason remain in the registry and snapshot.
- **Shutdown races with startup:** retain the startup promise, stop the connection first, then settle the promise before journal and lease shutdown.
- **Category change breaks consumers:** add the new field without removing existing categories and cover the JSON and browser projection in tests and documentation.
- **App Server response shape changes:** retain the pinned protocol profile and fail to unknown/degraded instead of inventing state.

## Exclusions

- Universal observation of unregistered Codex tasks.
- Remote Dashboard access, external notifications, or provider writes.
- Full-text conversation storage or search.
- Automatic task creation, rename, archive, approval, deployment, or release.
- Phase 4B policy evaluation and usage attribution; that follows in a separate Work Item after this fix passes.
