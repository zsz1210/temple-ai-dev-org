# Work order — WI-0029

## Accepted scope

Prototype an opt-in local Agent Command Gateway in the Temple Control Plane. A human may use the loopback Dashboard to send a visible new turn to an existing registered Codex task, steer its currently active turn, or request interruption.

The gateway remains disabled by default. It operates only through the configured local Codex App Server provider, only for registered non-terminal tasks whose Work Items are non-terminal, and only after an explicit preview confirmation. It does not create a Codex task, choose or switch a model, run in the background, cross a host boundary, expose a remote endpoint, retry automatically, release software, or publish the repository.

## Acceptance criteria

1. Configuration and the provider contract make command support explicit, opt-in, and loopback-only.
2. Every command includes an idempotency key, registered task identity, expected task and Work Item state, explicit confirmation, and bounded instruction text when the operation accepts text.
3. `new-turn`, `steer`, and `interrupt` map only to `turn/start`, `turn/steer`, and `turn/interrupt` for an existing registered provider thread. `steer` and `interrupt` require the exact observed active turn ID.
4. Stored local command records retain target identity, mode, timestamps, a bounded redacted preview, instruction length and digest, but never provider credentials or the complete instruction.
5. The Dashboard distinguishes `submitted`, `provider-accepted`, `turn-started`, `completed`, `failed`, `interrupted`, `provider-rejected`, and `delivery-unknown`. HTTP success is never presented as task completion.
6. Once a request may have crossed the provider boundary, a timeout or disconnect becomes `delivery-unknown` and is not retried automatically.
7. Deterministic tests cover successful dispatch, duplicate submission, disabled configuration, unregistered and terminal targets, stale task or turn state, explicit provider rejection, disconnect or timeout after dispatch, and loopback request protection.
8. A local runtime visual review proves the command preview, unavailable states, acknowledgement language, and recent-command projection. A real Codex turn remains a separately named validation boundary unless a disposable eligible task is explicitly authorized.

## Technical design

Add a top-level `agent_commands` configuration with `enabled: false` and a bounded `max_instruction_chars`. The existing loopback binding, Host and Origin validation, JSON limit, session secret, and idempotency checks remain mandatory. Starting the Codex observer does not implicitly enable commands.

The Human Inbox gains one bounded `agent-command` route. The route cannot accept a provider executable, shell command, model override, host, arbitrary thread ID, or new-task request. It addresses an existing registered task and carries optimistic-concurrency fields for the expected task status, Work Item state, provider thread ID, and active turn ID.

The provider exposes an eligible-target projection and tracks active turns from reconciled history plus live `turn/started` and `turn/completed` events. `new-turn`, `steer`, and `interrupt` map only to `turn/start`, `turn/steer`, and `turn/interrupt`. Explicit JSON-RPC errors become `provider-rejected`; successful start becomes `turn-started`; successful steering or interruption remains `provider-accepted` until a later observation; timeout or disconnect after dispatch becomes `delivery-unknown` and is never retried.

Stored command records retain target identity, operation, timestamps, a privacy-filtered bounded preview, instruction length and digest, and provider turn ID. They do not retain the full instruction or provider credentials. Recent command state correlates the stored turn ID with the privacy-filtered telemetry journal so an observed terminal turn becomes `completed`, `failed`, or `interrupted`.

## Risk review and rollback

- Idempotency prevents duplicate dispatch; uncertainty is persisted and never retried automatically.
- Task, Work Item, thread and active-turn expectations prevent stale or wrong-conversation delivery.
- Transport acknowledgement and execution state use separate fields and labels.
- Only a redacted preview, digest and length are retained locally; the UI warns against credentials.
- No remote option exists and the server remains loopback-only.
- Command capability is unavailable unless the configured provider is connected and implements the bounded methods.
- Deterministic fake-provider and fake-App-Server tests are required before any real-task validation.

Stop if target identity cannot be proven, protocol semantics differ, a command crosses the loopback boundary, instruction content leaks, idempotency fails, or a timeout causes replay. Roll back by leaving `agent_commands.enabled` false or reverting the feature commit. Existing observer and Human Inbox behavior must continue to work. Remote control, new-task creation, mutation of an existing production task, and release remain excluded.
