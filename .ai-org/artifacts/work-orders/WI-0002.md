# WI-0002 Work Order and Design

- Status: approved
- Approved at: 2026-08-30

- UX and UI owner positions: UX Designer and UI Designer
- Technical owner position: Tech Lead
- Implementation owner position: Developer
- Approval source: project owner direction recorded through the Temple self-hosting workflow

## Outcome

Give a first-time visitor a concise, human-first explanation of Temple: the coordination problem it solves, how its organization scales, what is usable today, and where to go next.

## Acceptance criteria

1. English is the canonical README and Japanese and Traditional Chinese are semantically equivalent.
2. The entry point addresses solo builders, collaborative teams, and enterprise organizations without implying that one profile is the default audience.
3. A compact horizontal diagram explains the operating loop without making the page unnecessarily tall.
4. Collapsible use cases let readers inspect only the scale relevant to them.
5. Current evidence, retained validation, and future benchmarks are visibly distinct.
6. SRE, Security, and production observability appear as enterprise extension directions, not completed capability claims.
7. Detailed implementation and operational material is routed into `docs/`.

## Content design

Use this order:

1. Name, language switcher, one-sentence promise, and alpha boundary.
2. A strong "Why Temple" section centered on coordination failure rather than feature inventory.
3. A compact left-to-right operating-loop diagram.
4. Collapsible solo, collaborative-team, and enterprise scenarios.
5. A scale model explaining that Positions are stable while Agent Identities and specialists can expand.
6. A short quick start and a proportionate-adoption tip.
7. Engineering methods, Skill extensibility, evidence boundaries, and human authority.
8. Documentation and license links.

Use GitHub callouts sparingly. Avoid release history, detailed command catalogs, and architecture archaeology in the public entry point.

## Organization model

The default self-host organization uses five named Agent Identities across ten stable Positions. This is a starter allocation, not a maximum. Frontend, backend, infrastructure, full-stack, data, SRE, and Security specialization can be represented through additional identities and disciplines. High-Assurance use must strengthen separation of duties, especially between implementation, evaluation, Independent QA, release, and security approval.

## Risk review

- **Marketing ahead of evidence:** label fixture-backed, locally verified, planned, and unverified claims distinctly.
- **Solo bias:** give each project scale equal conceptual status even when current validation is strongest locally.
- **Translation drift:** compare section structure, examples, cautions, and links across all three versions.
- **Excessive length:** use collapsible examples and route operational detail to the documentation index.
- **Diagram accessibility:** include an accessible title and description and repeat the essential meaning in prose.

## Exclusions

- No quantified savings claim until a benchmark includes a control baseline.
- No production SRE, SIEM, deployment, or incident-response integration in this Work Item.
- No claim that enterprise-scale multi-machine operation has been proven.
