# Work Order — WI-0017

## Outcome

Complete the local Phase 4B policy and daily-reliability contract without inventing Token measurements or assuming one Codex App Server process owns another host process's live session.

## Approved scope and design

1. Classify registered tasks by history-read eligibility, live-resume eligibility, and observed provider attachment outcome.
2. Convert known protocol failures into bounded reason codes. Do not keep reconnecting solely because a registered host-owned task cannot be resumed by this provider process.
3. Preserve provider-reported Token events as the only detailed usage source. Never estimate missing Token fields from text or elapsed time.
4. Add deterministic qualification over naturally completed Work Items, task shapes, correlated observations, and outcome evidence. Fewer than ten correlated Work Items remains `not-qualified`.
5. Add read-only recommendation output only when its evidence threshold is met. Recommendations never mutate model settings and never satisfy lifecycle gates.
6. Prove with adversarial tests that budget warnings and recommendations cannot skip context, Developer evidence, Independent QA, human approval, or release gates.

## Official capability boundary

Codex App Server supports `thread/read`, `thread/resume`, and active-thread Token usage notifications. Temple may observe only what the connected provider process can read or resume; a Desktop-owned or otherwise unavailable session remains a provider boundary, not a reason to fabricate history or usage.

## Verification

- Provider fixtures cover successful read and resume, terminal history-only tasks, unsupported or invalid resume, one-shot degradation, and no retry churn.
- Usage fixtures cover zero, partial, mismatched, stale, and ten-qualified correlated Work Items.
- Solo, Collaborative, and High-Assurance adversarial fixtures remain fail closed.
- The live self-host report records the actual provider outcome and leaves missing Token data unknown.

## Risk review

Token counts can become misleading policy signals. The implementation must retain provenance, distinguish observations from recommendations, and prevent any recommendation from acquiring approval, spending, or model-switch authority.

## Stop condition

Stop after the qualification and provider-boundary behavior is reproducible and the live result is truthfully classified. Do not create artificial tasks or paid calls to reach the ten-Work-Item threshold.

## Rollback

Revert the Phase 4B implementation commit and rebuild the generated usage view from the existing telemetry journal.
