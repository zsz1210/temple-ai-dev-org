# Work Order — WI-0014

## Outcome

Establish Temple's first provider-correlated active-task usage slice and extend the read-only Phase 4B report with a longitudinal coverage view. The result must distinguish canonical Work Item history, registered Codex task coverage, and detailed token observations without turning missing data into zero or making premature savings, cost, model-quality, or routing claims.

## Evidence entering Design

- Temple has 13 completed canonical Work Items, but its only registered Codex task is terminal and belongs to WI-0008.
- `temple usage preflight` can reconcile that historical task but reports no live resumable task and no detailed live observation.
- `temple usage report` therefore has no correlated token observations and correctly leaves token totals unknown.
- Phase 4B requires at least 10 varied real Work Items and a qualified longitudinal baseline before comparative efficiency claims are allowed.

## Approved scope and design

1. Add a deterministic longitudinal coverage section to the existing read-only usage report rather than creating a second source of truth.
2. Derive Work Item counts and lifecycle/task coverage only from canonical repository state and provider-owned observations.
3. Report completed Work Item coverage, registered-task coverage, live-versus-historical task eligibility, detailed token-observation coverage, and the remaining qualification gap.
4. Preserve `unknown` for unsupported token fields and keep prompt content, response content, hidden reasoning, prices, and inferred monetary cost out of persisted observations.
5. Register a fresh user-owned Codex task for WI-0014 before implementation begins, attach the local provider, and use that task as the first real active observation attempt.
6. Keep the first observation explicitly labeled as self-host dogfood evidence. It starts the longitudinal series; it does not by itself satisfy the 10-Work-Item qualification gate.
7. Do not implement automatic model routing, model switching, token budgets, price lookup, external tracker writes, push, publication, or deployment in this slice.

## Task start protocol

1. The new Codex task first verifies its exact base revision and pauses without edits.
2. The Engineering Manager registers the stable thread identity against WI-0014 and restarts or refreshes the local provider if required.
3. Preflight must show the new task as live and awaiting observation before the Developer is released to build.
4. After implementation activity, preflight or the usage report must either show a correlated detailed observation or record a truthful provider limitation. A missing event must never be fabricated.

## Verification

- Add focused fixture coverage for no tasks, historical-only tasks, one live task without detailed usage, one correlated detailed observation, and partially supported token fields.
- Prove generated output is deterministic and read-only under `--no-write`.
- Run the focused Phase 4B suite and full `npm run verify` at the exact candidate revision.
- Run fresh independent QA from a detached worktree at that same revision.
- Record the active-task observation outcome and its provenance in a validation note.

## Stop condition

Stop after WI-0014 has one truthfully classified active-task observation attempt, the longitudinal coverage report is independently verified, and the Work Item is locally closed. The broader 10-Work-Item baseline, comparative token claims, and model-routing recommendations remain future Phase 4B work.

## Rollback

Revert the candidate implementation commit. Canonical Work Items and registered task identities remain valid; generated provider observations can be rebuilt from their source without changing lifecycle authority.
