# WI-0006 Work Order and Technical Design

- Status: approved
- Approved at: 2026-08-30
- Engineering owner position: Tech Lead
- Documentation owner position: Developer
- Approval source: project owner approved the proposed Phase 4 design direction and added model selection and per-task token attribution

## Outcome

Define the contracts Temple must accept before Phase 4 implementation expands its persistence, evaluation, federation, usage-observation, or model-routing surfaces. The design must make token-heavy work traceable without turning token minimization into a substitute for correct delivery.

## Acceptance criteria

1. Canonical project truth, rebuildable runtime telemetry, read-only portfolio projections, and external provider authority remain separate.
2. Token accounting prefers provider-reported usage metadata and never invokes another model solely to count or classify tokens.
3. Usage can be attributed by project, Work Item, Position, lifecycle stage, Agent task, provider, and model when the provider exposes those dimensions; unavailable dimensions remain `unknown`.
4. Model routing defines defaults, eligible overrides, capability and risk constraints, spending boundaries, fallback behavior, and recorded effective configuration.
5. Phase 4A, 4B, and 4C have explicit implementation scope, exit evidence, stop conditions, and retained validations.
6. The ADR and documentation indexes route future maintainers to the accepted decisions.
7. Repository checks pass without claiming that the Phase 4 runtime features already exist.

## Technical design

- Add one Phase 4 plan that orders durability, evaluation, federation, operational metrics, and retained real-world validation.
- Add separate ADRs for durable recovery, adversarial evaluation, federated authority, and usage attribution plus model routing.
- Add an operations contract for Token Efficiency and Model Routing. Define measurement dimensions, provenance, budgets, routing precedence, fallbacks, privacy, and evaluation.
- Treat provider-reported usage as the preferred source. Permit a deterministic local estimate only when explicitly labeled as an estimate with tokenizer and version provenance.
- Keep monetary cost unavailable until a user-approved, versioned pricing source is configured.
- Make recommendations and warnings the initial behavior. Automatic model selection remains a later, opt-in capability that cannot weaken Position authority, approval gates, required context, or Independent QA.
- Index the new documents without expanding the public README in this Work Item.

## Research inputs

- The current Temple control plane already normalizes input, cached-input, output, reasoning-output, and total-token observations when a provider emits them.
- OpenAI's Responses API returns usage metadata with input, cached input, output, reasoning, and total token fields; consuming the response metadata does not require another inference request.
- Current OpenAI model guidance recommends evaluating model and reasoning configurations on representative tasks using quality, token, latency, and cost outcomes rather than assuming the highest or lowest setting is universally efficient.

## Risk review

- **False savings:** reducing context or model capability may increase retries, rework, defects, or total usage. Measure accepted outcome quality with usage.
- **Misattribution:** one Agent can hold several Positions, and one Work Item can use several tasks. Attribute usage to the effective Position and stage at event time, not display name alone.
- **Provider gaps:** some providers do not expose all usage or model fields. Preserve `unknown`; do not infer zero.
- **Pricing drift:** token counts are durable facts, but monetary cost depends on provider, model, service tier, cache behavior, currency, and a versioned price source.
- **Budget overreach:** a token budget is an alert or routing constraint, not permission to drop required evidence, skip QA, or authorize spending.
- **Sensitive context:** retain numeric usage and bounded identifiers, not raw prompts, hidden reasoning, tool payloads, or secrets.
- **Premature automation:** recommendations may ship before automatic routing. Automatic routing requires an evaluated policy, explicit enablement, and a safe fallback.

## Exclusions

- No Phase 4 persistence, portfolio, pricing, or model-routing implementation.
- No automatic model switching.
- No provider credential, purchase, API call, deployment, or external tracker mutation.
- No pricing table copied into canonical project state.
- No claim that measuring tokens alone improves cost or delivery quality.
