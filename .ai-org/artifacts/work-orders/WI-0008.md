# WI-0008 Work Order and Validation Design

- Status: approved for bounded rehearsal
- Approved at: 2026-08-30
- Engineering owner position: Engineering Manager
- Implementation owner position: Developer
- Approval source: project owner accepted the recommendation to validate Phase 4A before continuing Phase 4

## Outcome

Validate Temple Alpha.24 backup, stale-plan protection, restore, and cross-version upgrade behavior against the real AiPet repository while preserving the primary AiPet working tree. The rehearsal must produce reviewable evidence for Temple itself and must not continue AiPet product development.

## Starting point

- Temple is the system under test and records this rehearsal as `WI-0008`.
- AiPet is an external validation fixture at Temple Alpha.5.
- The primary AiPet checkout is clean at Git revision `28d53b483d0e5c5a21d9b483221393c3dd83ef77`.
- All mutations are restricted to an isolated detached Git worktree and an external rehearsal directory.
- Backup and restore observations gathered immediately before this Work Item was registered are preliminary evidence; they must be rechecked and recorded honestly rather than backdated as lifecycle evidence.

## Validation sequence

1. Confirm the primary AiPet checkout is clean and record its exact revision.
2. Inspect the external Alpha.5 backup and verify its manifest, file count, source revision, and content digest.
3. In the isolated checkout only, introduce one changed managed value and remove one backed-up artifact.
4. Prove the original restore plan is rejected as stale.
5. Create a fresh plan, apply it with explicit replacement permission, and compare every restored file digest with the backup.
6. Upgrade only the isolated checkout from Alpha.5 to Alpha.24.
7. Rebuild generated views and run Doctor against the upgraded isolated checkout.
8. Reconfirm the primary AiPet checkout remains clean and unchanged.
9. Record results and retained limitations in Temple's validation documentation.

## Evidence requirements

- Exact source and tested Git revisions.
- Backup manifest and content digests.
- Stale-plan rejection output.
- Fresh plan action counts and plan digest.
- Post-restore per-file digest comparison.
- Upgrade output, generated-state check, and Doctor result.
- Final primary-worktree cleanliness check.
- A clear distinction between verified behavior and retained future testing.

## Parallelism decision

Run sequentially. Backup, fault injection, restore, upgrade, and Doctor all mutate or depend on the same isolated checkout, so parallel execution would weaken causality and make evidence harder to attribute.

## Risk review

- **Primary-project mutation:** all write commands target the explicit isolated checkout; recheck the primary checkout after every mutation stage.
- **Fixture mistaken for product work:** do not edit AiPet features, UI, requirements, releases, or its primary branch.
- **False recovery claim:** compare every included payload digest; a successful command exit alone is insufficient.
- **Cross-version ambiguity:** record backup version, CLI version, upgrade-required state, and the post-upgrade Doctor result separately.
- **Generated-view noise:** distinguish project-owned canonical state from regenerated views and do not count generated diffs as restored payload mismatches.
- **Secret exposure:** keep the backup local and outside Git; do not print or commit backup payload contents.

## Stop conditions

- Stop immediately if the primary AiPet working tree becomes dirty or its revision changes.
- Stop if a command resolves the primary checkout instead of the isolated path.
- Stop if restore reports a conflict, project-ID mismatch, digest mismatch, or unrecoverable transaction.
- Stop after the bounded recovery and upgrade validation; do not begin AiPet feature development.

## Exclusions

- AiPet feature implementation, UI/UX work, releases, production operations, or repository restructuring.
- Remote backup, scheduled backup, encryption-key management, and full disaster-recovery certification.
- Phase 4B or Phase 4C implementation.
- Performance, high-concurrency, multi-machine, and large-enterprise validation; these remain retained tests.
