# Work order — WI-0028

## Accepted scope

Create the private GitHub release checkpoint for Temple `0.1.0-alpha.27`. The checkpoint may fast-forward `main`, wait for GitHub Actions, reproduce the pushed revision from a clean remote clone, and push one annotated `v0.1.0-alpha.27` tag only after all named gates pass.

Repository visibility must remain private. This work does not publish an npm package, create a GitHub Release, enable paid services, change branch or ruleset settings, force-push, delete refs, deploy software, or claim public, production, regulated, Windows, or multi-machine support.

## Technical design

1. Prove that `origin/main` is an ancestor of the candidate, the local branch is not behind, the tag is absent locally and remotely, and the authenticated remote is the intended private repository.
2. Inspect CI, version metadata, package contents, license, contribution, security, third-party provenance, tracked secret patterns, dependency audit, and the declared Node contract.
3. Verify the exact candidate locally on the maintainer environment and the declared minimum Node major. Record broader OS and npm-publication gaps as retained public-release work rather than silently broadening this private tag.
4. Commit the release-candidate evidence, fast-forward push `main`, and require the matching GitHub Actions run to pass.
5. Clone the private GitHub repository into a new disposable directory, prove the exact revision, install with the lockfile, run full verification, schema validation, Doctor, and the repository-pinned launcher, then remove only that disposable checkout.
6. Obtain fresh Independent QA at the exact pushed candidate. Close the organizational Work Item only after the evidence is accepted.
7. Push the final closeout commit, require its matching CI run to pass, create the annotated tag at that exact commit, push only that tag, and verify the remote ref and peeled commit.

## Stop conditions

Stop without a tag if the remote diverges, CI fails, the clean clone differs, the declared version is inconsistent, the tag already exists unexpectedly, release evidence cannot be reproduced, or any command would require force, visibility, publication, protection, credential, or paid-action expansion.

## Risk review and rollback

The branch pushes are additive fast-forwards. A failed candidate remains ordinary Git history and must be corrected by a new commit, never rewritten. The release tag is created only after every gate passes; after publication it is treated as immutable. A later defect receives a new version or corrective tag rather than deleting or moving `v0.1.0-alpha.27`.
