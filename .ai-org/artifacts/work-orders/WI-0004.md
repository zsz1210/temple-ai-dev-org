# WI-0004 Work Order and Content Design

- Status: approved
- Approved at: 2026-08-30
- Product and documentation owner position: Product Manager
- Implementation owner position: Developer
- Approval source: project owner rejected the current audience copy and requested a reader-first rewrite

## Outcome

Make the scenario section answer one immediate question: who Temple is for and how it helps them. A reader should understand the individual, team, and enterprise cases before encountering Temple's internal vocabulary.

## Acceptance criteria

1. The section heading states who Temple is for in plain language.
2. The three collapsible labels are concise audience names: individual developer, development team, and enterprise organization.
3. Each description starts from a recognizable working situation, then explains Temple's benefit, and only then introduces the minimum framework terminology needed.
4. The copy clearly distinguishes current validated behavior from retained large-scale validation and future SRE or Security directions.
5. English, Japanese, and Traditional Chinese preserve the same structure and meaning in natural language.
6. Repository documentation checks pass.

## Content design

- Replace the vague invitation heading with `Who is Temple for?` and natural equivalents.
- Use audience labels rather than labels that encode every implementation detail.
- Explain continuity, task boundaries, parallel work, and adoption through reader problems instead of internal nouns.
- Keep one explicit current-validation sentence in each audience block so the public README does not overstate evidence.
- Preserve the collapsible layout and the following Position and scaling section.

## Risk review

- **Marketing drift:** retain the current solo-validation, pending large-scale validation, and planned enterprise-extension boundaries.
- **Translation drift:** edit all three language files together and compare structural counts.
- **Terminology overload:** introduce only terms that the paragraph immediately explains.
- **Loss of precision:** preserve repository authority, Developer/Independent QA separation, integration ownership, and external-tracker boundaries.

## Exclusions

- No new framework capability or optional Skill installation.
- No change to the operating model, Positions, or validation roadmap.
- No README sections outside the audience scenarios.
