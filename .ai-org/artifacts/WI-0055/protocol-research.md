# Codex App Server protocol research

## Official lifecycle

The official App Server documentation describes `thread/start` as the new-thread boundary, `turn/start` as the generation boundary, and `model/list` as the capability-discovery boundary:

- <https://developers.openai.com/codex/app-server/>

The official page establishes the method lifecycle but does not replace the exact schema generated by the installed CLI.

Observed values:

| Boundary | Field | Current values |
|---|---|---|
| `thread/start` | `sandbox` | `read-only`, `workspace-write`, `danger-full-access` |
| `thread/start`, `turn/start` | `approvalPolicy` | `untrusted`, `on-request`, `never`, or the documented granular object |
| `turn/start` | `sandboxPolicy.type` | `dangerFullAccess`, `readOnly`, `externalSandbox`, `workspaceWrite` |

Temple intentionally exposes neither `danger-full-access` nor granular approvals through the Provider-owned primitive in this slice.

## Root cause carried from WI-0054

Temple used internal camelCase labels directly for `thread/start.sandbox`. Mock tests accepted the same values and therefore reproduced Temple's assumption rather than the installed protocol.

The same audit also found that the internal approval vocabulary included `onFailure`, which has no current string equivalent in the installed v2 schema. It must fail before the Provider boundary rather than be guessed.
