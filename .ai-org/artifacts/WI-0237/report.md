# Evaluation reliability review and input audit

## Decision

**Do not launch another efficiency comparison in this phase.** The instrument
corrections are useful, but are not an input-efficiency treatment. No new model
comparison, fallback, reset, Credits purchase or release was performed. Normal
development/review of this change still consumes resources; that cost is not zero
and is not included in historical subject Token totals.

WI-0236 remains an incomplete three-of-four attempt. Its stable pair still costs
75,433 versus 19,272 Operational Tokens with equal product acceptance. Neither this
review nor the revised oracle rescored or completed that frozen experiment.

## Corrections delivered

1. **Product versus delivery revision.** An explicit new qualification mode tests
   the reported product commit while allowing a later record-only descendant.
   It checks ancestry, exact non-record bytes/modes, unchanged approved item
   scope, matching released claim/handoff, candidate-citing evidence, receipt
   request digest and an append-only item-scoped event suffix. Only named record
   paths are exempted from candidate/final equality. Dirty records, altered
   product/tests, unrelated history, arbitrary artifacts and stale evidence fail.
   The old exact-HEAD oracle remains the default for historical compatibility.
2. **Shared acceptance decisions.** The native runner now uses the same typed
   assessment/continuation decision as the earlier evaluation sequence. A known
   isolated product/acceptance failure retains its cost and can continue only
   under the frozen continuation policy. Runtime/cleanup/usage uncertainty,
   invalid candidates and unclassified oracle failures remain global stops.
   A completed batch with failed acceptance is explicitly labeled
   `completed-with-failures`, never an all-pass batch.
3. **Useful bounded observations.** A single literal native shell wrapper is
   recognized without execution. Compound scripts remain unknown. `sed -i`, sed
   execution/write scripts and `rg --pre` are not labeled reading. Output bytes,
   duplicates and missing data remain bounded and explicit; raw command/output
   text is not retained in aggregate observations.
4. **Same-path offline qualification.** A shared control performs real installed
   claim, product tests, finish and a separate record commit. Both regression
   tests and live preparation use it. Preparation additionally checks native
   observation formats. The new protocol version rejects old approvals before
   consumption. This is preparation safety, not authority for another run.

Observation categories describe coarse commands, not semantic execution or file
consumption. Synthetic format coverage is not measured native-session coverage.
Old command hashes cannot recover the raw commands that were deliberately not
retained, so the original 32 unknown categories must stay unknown.

## Required-input audit

The retained WI-0236 installation contains 27,200 bytes across native AGENTS,
TEMPLE, the Work Skill and the Lean execution reference. Its stable SPEC and
HANDOFF total 1,333 bytes. This is an inventory observation, not proof that each
body was read again or an explanation of provider cache behavior.

A fresh changed-spec synthetic fixture produced this separate, generation-free
measurement through the actual entry and compact navigation paths:

| Surface | UTF-8 bytes | Interpretation |
| --- | ---: | --- |
| Four operating instruction bodies | 27,200 | Present in the selected material set |
| Current product SPEC and HANDOFF | 1,400 | Same fixture facts, not the older stable condition |
| All selected source bodies | 74,626 | Includes policy, identity/state and lock metadata |
| Optional full entry JSON | 103,664 | Selected bodies plus serialized navigation/provenance |
| Compact navigation JSON | 4,827 | No source bodies; required reads still follow |
| Whole lock file inside the selected set | 20,526 | Inventory data, not 20,526 bytes of product rules |

These numbers are from one fixture invocation. Timestamps and revision references
can change other invocation sizes. The full-entry versus compact-navigation
difference is **not savings**: one delivers bodies and the other does not. The
existing WI-0236 treatment already allowed compact navigation, so changing to it
again would not be a new experimental variable.

Retained completed-command exit observations were: ordinary stable 1 nonzero of
8, Temple stable 0 of 12, Temple changed-spec 1 of 12. The slow Temple stable sample
does not show a sequence of failed shell commands. That narrows the investigation;
it does not rule out repeated successful reads or redundant successful operations.

### Obligation disposition

| Material/work | Needed by the Agent | Tool responsibility | Disposition |
| --- | --- | --- | --- |
| Current product scope and acceptance | Yes, before implementation | Bind current authority, never infer product truth | Preserve |
| Native/project instructions | Applicable instructions, including whole reads explicitly required | Detect drift, not claim comprehension | Preserve; do not silently replace with a generated summary |
| Position, identity, claim, next owner | Current actor and decision boundary | Validate eligibility, sponsorship, ownership and transition | Investigate repeated whole registries, without omitting governing rules |
| Framework lock inventory | Exact ownership boundaries when relevant | Validate hashes and managed paths | Largest explicit inventory candidate; current task projection already exists and is not a new treatment |
| Alternate delivery recipes | Only the selected applicable route | Execute the supported operation | One finish path is already in WI-0235; do not count it as a second improvement |
| Successful unchanged diagnostics | Inspect the result once | Finish already runs full diagnostics | Preserve existing reuse; do not remove failed checks |
| Reports and handoff | Exact evidence, actual blockers and next owner | Store the durable receipt and handoff | Avoid duplicated narrative; do not delete evidence |
| Native prefix, tool output and cache | Unknown complete provider composition | Collect bounded observations when a new run is justified | No per-file Token attribution from these byte counts |

## Why this phase stops without a live comparison

The actual subject Token excess is mostly uncached input, but the prior run does
not identify the responsible read sequence. The obvious representation switches
and one-finish recipe have already been tried or are already optional. Repeating
them would not test a new intervention. Blanket removal of native/policy reads
would change the authority contract, not merely remove metadata.

Therefore this phase retains the instrument corrections and reproducible audit,
but makes **no instruction, role, model, profile, package or default-routing
change**. This is a deliberate no-go for another efficiency batch, not a deferred
request to approve the same comparison again. There is no quantitative reduction
claim for this implementation.

## Next design target, not an automatically launched experiment

The next useful proposal is a smaller task operating contract: decide which
operation-specific facts the Agent must consume and which validations the CLI
already owns. First specify obligations, preserve whole-source exceptions and
test contradictory/project-owned instructions; only then consider changing the
default entry. Do not add a Position, router or second execution engine.

A future live comparison needs a real candidate that removes named mandatory
work while preserving the same authority and acceptance conditions, an explicit
practical decision it can change, and a frozen bounded protocol. Synthetic bytes
alone cannot supply a Token target, statistical significance or a marketing claim.
Collaboration/recovery value remains a separate hypothesis; a larger task must
not be used to hide the unfavorable small-task result.
